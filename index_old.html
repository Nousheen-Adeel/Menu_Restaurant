HOW AN ORDER GETS FILLED

Every request is a ticket to the kitchen.

A request comes in, the kitchen (FastAPI) checks what's on hand, and a receipt goes back out. No database — the whole menu lives in memory, ready to serve.

01

Customer orders

A GET request hits /menu, optionally naming a category.

→
02

Kitchen checks stock

The route function scans the in-memory MENU list for a match.

→
03

Receipt printed

A validated MenuResponse goes back as JSON — or a 404 if nothing matched.

THE MENU BOARD

Three ways to place an order.

Each endpoint is its own order slip — what you ask for, what the kitchen does with it, and what comes back on the receipt.

GET /menu

See the whole menu

No category given — the kitchen hands over every dish, available or not, exactly as it sits on the shelf.

REQUEST
GET /menu
RECEIPT
{
  "count": 18,
  "items": [ ...all dishes... ]
}
GET /menu?category=Pizza

Ask for one course

A category name narrows the search. Nothing matching that name means a clear "sold out" answer, not an empty plate.

REQUEST
GET /menu?category=Pizza
RECEIPT (or 404)
{
  "count": 3,
  "items": [ ...pizzas... ]
}
// unknown category → 404
GET /menu/{id}

Look up one dish

A specific dish number, by table lookup. If that number was never on the board, the kitchen says so plainly.

REQUEST
GET /menu/4
RECEIPT (or 404)
{
  "count": 1,
  "items": [ { "name": "Chicken
    Alfredo Pasta", ... } ]
}
